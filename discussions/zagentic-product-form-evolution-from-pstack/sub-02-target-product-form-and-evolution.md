# 目标产品形态与演进路径：ZAgentic 应如何前进

> 本文件对应 MASTER 索引中的第二项，按“一事一议”原则独立讨论与求解，由 `zj-discuss` + `zj-discuss-view` 维护。

## 上下文

- **所属主文档：** [../MASTER.md](./MASTER.md)
- **本子问题独立性：** 本文从 ZAgentic 当前用户任务、入口和治理边界出发，选择目标产品形态并定义最小可逆验证；它可独立评估，不以子文档 1 先给出最终结论为前提。本文将“组合器”定义为意图到 Plan 的方案生成能力，将“Plan”定义为组合器 skill 内置模板生成的可审查方案契约。
- **成功判据：** 至少比较保持现状、可解释组合器/方案生成器、有限状态薄编排层和强 router/runtime；明确一个推荐形态或暂不演进的理由；写出输入、输出、状态、失败出口、Human 决策点、owner 边界；给出可逆 PoC、测量方法、成功阈值、停止条件和回退路径。
- **声明必需角色集：** B,C,A,U,T,S

## 待讨论问题（scope 草案）

- Q1：当前“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”旅程的主要摩擦在哪里？哪些是 skill 缺口，哪些是产品体验缺口？
- Q2：四种候选形态各自解决什么、引入什么成本，适用边界是什么？
- Q3：推荐形态的输入、输出、状态、失败表现、Human 决策点和不可逆动作边界是什么？
- Q4：哪个最小纵切能证明用户组装成本下降，同时不产生第二 authority、隐式副作用或 runtime 锁定？
- Q5：用什么指标决定继续、修改或停止，如何保留回退路径？

## Agent viewpoints（独立视角 — 须跨会话独立 Agent）

> 每个视角必须由声明角色的独立 Agent `Read` 本文件原文后撰写；每个观点块都要带“发现 / 影响 / 建议”和原文定位。

### 视角：B（技术经理 / 可落地）

`视角来源: 跨会话独立Agent`

**观点 1：先补基线与任务白名单，否则无法排期

- **发现**：原文“成功判据”要求比较四种形态、定义输入输出和可逆 PoC；`Q1` 只提出寻找“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”中的摩擦，没有给出代表性任务、当前耗时、返工次数或负责人。（原文 L12-L18）
- **影响**：没有基线就无法估算收益和人力，也无法判断是补 skill 还是做产品入口。范围很容易从降低组装成本膨胀为新的 router/runtime，关键路径和完成边界会失控。
- **建议**：先做一个 1–2 人日的基线阶段，固定三个真实任务和任务负责人，记录从任务描述到可执行方案的耗时、人工选择次数、失败/返工次数及需要的外部动作。基线表、任务白名单和指标口径由产品与技术共同签字后，才进入形态 PoC；没有这三项材料的候选不进入排期。

**观点 2：四种形态必须按依赖阶梯比较，先交付可撤回的薄层

- **发现**：原文 Q2` 要求比较“保持现状、可解释组合器/方案生成器、有限状态薄编排层和强 router/runtime”，但当前 scope 没有列出各候选的依赖、owner、成本或迁移路径。（原文 L12-L18）
- **影响**：四个候选的工程量并不在同一量级。强 router/runtime 至少会引入调度、状态持久化、权限和故障恢复等长期 owner；若先做它，验证“组合成本是否下降”前就承担了运行时维护成本，并形成难以回退的路径依赖。
- **建议**：在决策记录中增加四候选矩阵，至少列出依赖组件、预计人日、需要新增的长期 owner、可回退方式和完成证据。把第一阶段限定为复用现有 skill 索引的可解释方案生成器（建议 5–8 人日，含契约、实现和三任务验证）；只有基线证明“只给方案仍不能完成任务”时，才开启薄编排层的独立闸门。强 router/runtime 暂不列入首个交付。

**观点 3：首个纵切应只拥有“生成方案”这条责任链

- **发现**：原文 Q3` 要求定义推荐形态的输入、输出、状态、失败表现、Human 决策点和不可逆动作边界，但目前这些字段仍为空；`Q4` 又要求证明不产生第二 authority、隐式副作用或 runtime 锁定。（原文 L12-L18）
- **影响**：如果 PoC 同时负责自动选 skill、执行、验证和沉淀，任何一个环节的失败都会被误判为组合器失败，且会出现新的状态 owner。交付验收会变成“能演示”而非“能界定责任”，回退也需要恢复运行时状态。
- **建议**：把首个纵切契约固定为：输入是任务描述、约束和可用 skill 索引；输出是有顺序的 skill 组合、选择理由、前置条件、风险和预期产物；状态只有 `draft → approved / rejected / expired`。Human 在 `approved` 前必须确认，PoC 不执行写文件、推送、发布或外部调用；执行仍由现有 skill 和既有 Git/文档治理流程负责。完成标准是三个基线任务均能生成可审阅方案，且每个方案都有 owner、失败出口和人工确认记录。

**观点 4：依赖和 ownership 要写进契约，避免形成第二 authority

- **发现**：原文“成功判据”要求明确 owner 边界，`Q3` 要求定义不可逆动作边界；原文上下文又把本子问题定位为从 ZAgentic 当前入口和治理边界出发，但没有指定方案生成器与 skill、文档治理、Git 操作之间的责任分界。（原文 L12-L18）
- **影响**：如果生成器缓存一份可执行流程、重写 skill 元数据或自行判定验证通过，它就会与现有 skill discovery、证据和 Human 决策形成竞争 authority。后续每次 skill 变更都需要同步两套语义，维护成本会持续增长。
- **建议**：在 PoC 开工前写一页 ADR：生成器只读现有 skill/规则索引，只产生带版本和来源的计划文件；skill 文件、证据、Git 安全和最终批准仍各自归原 owner；计划过期或索引版本变化即失败并要求重新生成。把“无第二 authority、无 skill 自动改写、无不可逆副作用”列为阻断式验收项，并由架构与技术负责人签收。

**观点 5：先定义数值闸门和无迁移回退，才能判断继续还是停止

- **发现**：原文 Q4` 要求给出“成功阈值、停止条件和回退路径”，`Q5` 再次要求用指标决定继续、修改或停止，但当前文档只提出问题，没有阈值、观测周期或回退动作。（原文 L12-L18）
- **影响**：没有数值闸门，团队会用一次成功演示替代产品验证；没有回退动作，PoC 一旦写入现有 skill 或运行时就无法区分实验失败和系统损坏，后续只能继续投入以摊平沉没成本。
- **建议**：为三个基线任务各跑至少两次基线和两次 PoC，预先约定“从任务到可审阅方案的中位耗时下降至少 30%、人工选 skill 次数下降至少 25%、方案字段完整率 100%、未经批准的写入/外部动作 0 次”为继续门槛；任一安全门槛失败立即停止。使用显式实验入口或开关，首版不迁移数据、不改写 skill、不创建持久 runtime 状态；不达标时删除入口和临时计划即可回退，达标后再单独评审是否进入薄编排阶段。

### 视角：C（产品专家 / 用户价值·生态竞品）

`视角来源: 跨会话独立Agent`

**观点 1：第一产品承诺应是“可解释的组合方案”，而不是自动执行的 router。**

- **发现**：原文 ## 上下文` 的成功判据要求比较四种产品形态，并同时交代输入、输出、状态、失败出口和 Human 决策点（原文 L8-L10）；原文 Q1 又把用户旅程写成“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”（原文 L12-L18），但没有指定哪类用户在何种任务下需要哪一种形态。
- **影响**：如果直接把“自动选 skill / 自动串 workflow”当作产品价值，用户只能感知到路由结果，无法判断为什么被推荐、如何替换或失败后从哪一步恢复。这会把 ZAgentic 与强 router 的便利性绑定，却没有形成可解释、可迁移的采用理由；新用户的首次选择成本和维护者的排错成本都可能上升。
- **建议**：以“用户任务 + 仓库状态 + 约束”作为输入，先产出一份可编辑的组合方案：候选 skill、执行顺序、每一步的预期产物、选择理由、已知冲突、验证点和退出路径；默认停在 Human 决策点，由用户批准后再执行。把“保持现状 + `zj-guide` 推荐路径”作为控制组，把“可解释组合器”作为第一候选，使用同一组代表任务比较首次成功时间、方案采纳率、用户能否解释每个选择和失败后的恢复率。

**观点 2：产品差异应落在“可复用的能力配方”和生态闭环，而不是增加一层不可见运行时。**

- **发现**：原文 Q2 要求比较保持现状、可解释组合器、有限状态薄编排层和强 router/runtime（原文 L14-L15）；原文 Q4 明确要求降低用户组装成本，同时避免第二 authority、隐式副作用和 runtime 锁定（原文 L16-L18）。这说明产品竞争点必须同时覆盖一次任务效率和长期复用边界，而不能只用单次自动化成功来验收。
- **影响**：若 PoC 只测“这次是否跑完”，用户完成后仍会丢失组合理由、验证证据和适用约束，生态无法沉淀可分享的能力；强 runtime 还会让技能作者被迫适配一个新的状态和路由协议。相反，若组合结果本身是可读、可审查、可再次触发的配方，ZAgentic 可以用低迁移成本积累推荐路径，并用 pstack-claude 的自动路由作为外部对照，验证“解释性与可回退性”是否带来真实采用价值。
- **建议**：PoC 输出一个版本化的 Markdown 方案包，至少包含任务目标、输入约束、选中/排除的 skill 及理由、执行顺序、证据与验证结果、失败恢复和适用范围；允许用户手工修改后再次执行，也允许删除方案包并回到现有 native 路径。为新用户、熟悉 skill 的开发者、维护者分别设置任务样本，继续的门槛建议为：首次成功时间相对控制组下降 ≥30%，方案中关键选择的可解释率 ≥80%，同一方案第二次复用成功率 ≥70%，且 authority bypass、不可逆副作用和无法回退的运行时依赖均为 0；任一硬门槛失败则停止扩展到薄编排层，回退为现状 + 推荐路径。

### 视角：A（架构师 / 约束）

`视角来源: 跨会话独立Agent`

**观点 1：先把用户旅程摩擦映射到唯一 owner

- **发现**：原文 Q1 要求定位“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”各阶段的摩擦，并区分 skill 缺口和产品体验缺口（原文 ## 待讨论问题（scope 草案）` Q1）；但成功判据没有要求给出阶段状态、语义 owner 或现有入口与新入口的边界（原文 ## 上下文` 的“成功判据”）。
- **影响**：同一摩擦可能被重复修复：一部分写入 skill，一部分写入组合器，最后形成两套选择规则和两个事实来源。随着 skill 数量增长，用户看到的推荐可能与 skill 自身的前置条件不一致，回退时也无法判断应删除体验层还是能力层。
- **建议**：先建一张旅程契约表，逐阶段记录入口、输入、输出、状态 owner、权限、失败出口和持久化位置，并给每个摩擦标注唯一修复 owner。产品层可以生成建议，但 skill 的能力语义、现有治理文档和 Human 决策仍保持唯一 owner；评审通过“同一输入是否只有一个可解释的前置条件来源”作为边界闸门。

**观点 2：四种候选形态必须用不变式筛选，而不是只比功能

- **发现**：原文 Q2 要求比较“保持现状、可解释组合器/方案生成器、有限状态薄编排层和强 router/runtime”，并说明各自成本与适用边界（原文 ## 待讨论问题（scope 草案）` Q2）；但文档没有先声明候选形态共同必须遵守的 authority、向后兼容和运行时隔离不变式。
- **影响**：四个候选会被当作功能强弱的连续光谱，强 router 可能因短期自动化收益胜出，却悄然接管 skill 发现、权限判断或验证语义。此时新增层与 ZAgentic 现有治理的耦合会随 skill 数量和历史产物数量累积，删除或降级将不再是局部操作。
- **建议**：在候选矩阵前固定架构不变式：现有 skill 与治理文档保持语义 owner；新层默认只读并生成可审计方案；任何执行需显式批准；没有新 runtime 时原有 skill 路径仍可工作；新层可整体移除而不改写历史产物。按这些闸门重评四种候选：组合器可作为默认探索层，薄编排层仅在协议稳定后实验，强 router/runtime 置于隔离试验区，直到证明不会形成第二 authority。

**观点 3：推荐形态需要版本化的计划与运行契约

- **发现**：原文 Q3 要求明确推荐形态的输入、输出、状态、失败表现、Human 决策点和不可逆动作边界（原文 ## 待讨论问题（scope 草案）` Q3）；但当前文本没有定义这些字段的 schema、状态迁移规则、版本兼容策略或跨宿主接口。
- **影响**：一个“方案生成器”可能从建议直接滑向执行器；暂停、重试、失败恢复和升级时，调用方无法知道哪些状态可安全重放，哪些副作用已经发生。缺少版本契约也会让旧 skill 与新组合层之间出现隐式字段依赖，升级成本随组合数量增长。
- **建议**：定义窄而版本化的 `Plan`/`Run` 契约：输入含目标、约束、候选 skill、证据要求和权限；输出含有序步骤、来源、预期产物、验证规则和未决风险。状态至少覆盖 `proposed → approved → running → blocked/failed → verified → recorded`，另设 `cancelled`；每个迁移标注 owner、允许副作用、人工决策点和恢复输入。未知字段必须可忽略，未知状态必须安全暂停，保证协议可演进。

**观点 4：最小纵切应只增加可删除的适配层

- **发现**：原文 Q4 要求最小纵切证明组装成本下降，同时不产生第二 authority、隐式副作用或 runtime 锁定（原文 ## 待讨论问题（scope 草案）` Q4）；但没有规定“可逆”如何验证，也没有限定 PoC 的写入范围和回退动作。
- **影响**：PoC 若直接修改 skill、全局路由或运行时配置，即使指标改善，也无法判断收益来自组合体验还是来自不可逆的基础设施变化；失败后可能留下索引、状态或权限残留，使基线不再可重建。
- **建议**：把首个纵切限制为一个显式调用的方案生成器：读取现有 skill 元数据，输出带来源和验证要求的 `Plan` 文件，由 Human 批准后沿现有执行路径完成；禁止自动修改 skill、全局索引、权限和长期治理文档。验收包含“删除生成器目录后基线任务仍可运行”“历史 Plan 可读取”“失败不会产生未声明副作用”三项回退测试，均通过才扩大范围。

**观点 5：继续、修改和停止必须绑定接口兼容闸门

- **发现**：原文 Q5 要求用指标决定继续、修改或停止，并保留回退路径（原文 ## 待讨论问题（scope 草案）` Q5）；成功判据还要求给出测量方法、成功阈值、停止条件和回退路径（原文 ## 上下文` 的“成功判据”），但未指定谁拥有版本升级、数据迁移和回退决策。
- **影响**：即使 PoC 的用户指标达标，架构债务可能继续积累：接口变更没有兼容窗口，产物无法由旧版本读取，或停止实验后无法清理新增状态。缺少 owner 会使“继续”成为默认选择，并把试验协议误固化为长期产品契约。
- **建议**：把每个门槛拆成两类：用户结果门槛（组装时间、成功率、恢复率）和架构门槛（无第二 authority、旧 skill 可独立执行、Plan 可版本化读取、删除后基线通过）。由 ZAgentic 现有治理 owner 批准协议升级和回退；任一架构门槛失败即停止扩大、保留实验隔离并删除适配层。只有连续两个固定版本窗口通过，才考虑把薄编排层纳入默认入口。

### 视角：U（用户研究 / UX）

`视角来源: 跨会话独立Agent`

**观点 1：先把抽象旅程还原成真实任务，才能定位体验断点

- **发现**：原文 Q1` 把流程写成“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”，要求区分 skill 缺口和产品体验缺口，但没有指定用户类型、真实任务、使用环境或观察方法；原文“成功判据”也没有要求用户分层。（原文 L12-L18）
- **影响**：这条线性链路可能掩盖不同用户的断点：新用户可能卡在发现，熟悉用户可能卡在组合和验证，维护者可能卡在沉淀。没有现场证据，团队会把认知负担误判成缺 skill，或把能力缺口包装成更复杂的入口；首次成功时间和中途放弃率也无法解释。
- **建议**：在 PoC 前观察至少三类用户（首次使用者、熟悉 skill 的开发者、维护者）各完成一个真实任务，记录每一步的进入条件、停顿、回退、提问和放弃原因。输出一张“阶段 × 用户 × 断点 × owner”的旅程表；每个断点必须标为 skill 缺口、产品体验缺口或证据不足，并用一次复测确认修复有效。

**观点 2：组合选择应降低认知负担，而不是把四种形态交给用户决策

- **发现**：原文 Q2` 要求比较“保持现状、可解释组合器/方案生成器、有限状态薄编排层和强 router/runtime”，但没有规定比较结果如何呈现给使用者，也没有说明用户需要理解哪些技术差异。（原文 L12-L18）
- **影响**：如果把候选形态、skill 名称、运行状态和依赖同时暴露，用户会先学习系统结构，再完成自己的任务；选择越多，越难判断为什么某个 skill 被选中或排除。强 router 可能暂时减少点击，却会把“不理解也要接受”的风险转移到失败恢复和维护阶段。
- **建议**：让产品默认给出一条可编辑的推荐路径，并采用渐进披露：首屏只显示目标、下一步、预计产物和需要确认的事项；展开后再显示候选、排除理由、前置条件和替代方案。为每次推荐提供“为什么选它 / 我如何改 / 失败后回哪里”三个固定入口。可用性验收要求至少 80% 的受试者能复述下一步和选择理由，且无需先阅读 runtime 术语表。

**观点 3：Human 决策点必须是可理解、可撤回的工作台，不应成为阻塞对话框

- **发现**：原文“成功判据”要求写出 Human 决策点，`Q3` 要求定义输入、输出、状态、失败表现和不可逆动作边界，但当前文档没有规定用户在批准前能看到什么、能编辑什么，也没有定义拒绝或返回后的路径。（原文 L12-L18）
- **影响**：若批准只是一个“继续”按钮，用户无法检查组合是否符合自己的目标；若拒绝后只能重新开始，任何一次不确定都会造成整条流程重做。用户会绕过入口回到熟悉的手工路径，测试数据也会把“未批准”误记为能力失败。
- **建议**：把批准前的产物定义为可编辑方案页：显示目标、输入约束、步骤顺序、预期产物、证据要求、风险和待确认项；用户可以替换、删除或重排步骤，并保留原方案作为版本。明确 `draft / approved / rejected / expired` 的可见状态，`rejected` 必须能携带原因回到编辑态，`expired` 必须说明是哪一项 skill 或约束变化导致失效。

**观点 4：失败恢复要保留上下文，并给出下一步可执行动作

- **发现**：原文 Q3` 要求失败表现，`Q4` 要求最小纵切避免隐式副作用和 runtime 锁定，`Q5` 要求保留回退路径；但没有规定失败消息的内容、用户能否重试单步或如何回到现有路径。（原文 L12-L18）
- **影响**：只显示“组合失败”会迫使用户重新描述任务，增加重复输入和焦虑；自动重试或跳过又可能让用户误以为整个方案仍然有效。若失败后遗留不可见状态，用户无法判断回退是否真的完成，也无法建立对推荐结果的信任。
- **建议**：每个步骤的失败信息至少包含原因、受影响的步骤、已产生的产物、可安全重试的范围和人工替代动作；支持编辑约束后重算、从失败步骤继续、放弃方案并回到现有 native 路径。用“缺失 skill、冲突约束、验证失败”三类故障做可用性测试，验收为用户无需重新输入任务即可完成重试或明确退出，且能说出是否产生了副作用。

**观点 5：可达性与可读性必须进入首个 PoC 的体验门槛

- **发现**：原文“成功判据”和 `Q1`–`Q5` 覆盖了流程、形态、状态、Human 决策、指标和回退，却完全没有提到可达性、无障碍或不同输入方式；当前也未声明首个入口是命令行、Markdown 方案还是图形界面。（原文 L12-L18）
- **影响**：如果方案依赖颜色、悬浮提示、鼠标操作或不可复制的可视化，部分用户无法完成关键确认；即使平均耗时下降，实际采用仍会集中在熟悉环境的少数用户，且错误信息难以被复制、搜索和协作。入口形式未定会让无障碍要求在后期变成重做成本。
- **建议**：在 PoC 契约中先规定格式无关的可达性基线：所有关键状态和风险都有纯文本标签，颜色不是唯一提示，方案可复制、可搜索、可键盘完成，错误信息包含稳定的步骤名和原因；若采用界面，再增加键盘焦点顺序、屏幕阅读器语义和缩放测试。至少让一名使用辅助技术或仅用键盘的测试者完成“查看 → 修改 → 批准 / 拒绝 → 恢复”全流程；无法完成即不通过体验闸门。

### 视角：T（测试 / 质量）

`视角来源: 跨会话独立Agent`

**观点 1：先把四种候选形态变成同一任务集上的可重复对照实验。**

- **发现**：原文成功判据要求比较保持现状、可解释组合器、有限状态薄编排层和强 router/runtime，并定义输入、输出、状态、失败出口和 Human 决策点（原文 L8-L10）；Q1-Q2 只提出要定位旅程摩擦和比较成本/适用边界，没有给出固定 fixture、基线或判定 oracle（原文 L12-L15）。
- **影响**：如果各候选使用不同任务或靠演示判断，无法区分 skill 能力缺口、入口体验改进和运行时自动化收益；一次成功也不能证明可复现。产品决策会被样例偏差推动，测试无法回答“组装成本是否真的下降”。
- **建议**：建立版本化的任务 fixture，至少覆盖一个新任务组装、一个已有 skill 组合和一个失败恢复场景；对当前路径与每个候选使用相同输入、skill 索引快照和权限。自动校验每份结果是否包含任务目标、选中项及理由、顺序、前置条件、预期产物、验证点、失败出口和 Human 决策点，并记录首次成功时间、人工修正次数、任务成功率和结果可复现性。未完成同 fixture 的基线与候选对照，不得把 PoC 结果升级为产品结论。

**观点 2：异常和拒绝路径必须成为一等测试场景，并默认验证无副作用。**

- **发现**：Q3 明确要求定义状态、失败表现、Human 决策点和不可逆动作边界，Q4 要求最小纵切不产生隐式副作用（原文 L16-L17）；但当前 scope 没有列出空输入、冲突、过期或部分完成等边界 case。
- **影响**：只测完整、清晰、有匹配 skill 的 happy path，可能把“无法安全组合”误报为成功，或在用户拒绝后仍留下文件、状态和外部写入。此类错误会同时污染成功率、恢复率和回退测试，且最难从演示中发现。
- **建议**：为方案生成和执行入口建立负例矩阵：空/含糊任务、无匹配 skill、互相冲突的 skill、索引或来源过期、缺少必需前置条件、Human reject/cancel、重复提交、执行中断和并发生成。每个负例必须断言：状态进入明确失败/阻塞/拒绝、说明原因与下一步、不会发生未批准的文件修改、Git 操作、外部调用或持久 runtime 状态；重复运行应得到可比结果，或明确记录受版本变化影响的原因。

**观点 3：回归与移除测试要证明新增入口不会夺走现有能力。**

- **发现**：原文 Q1 覆盖安装、发现、选择、组合、执行、验证和沉淀的完整旅程，Q5 要求用指标决定继续/修改/停止并保留回退路径（原文 L14-L18）；成功判据还要求明确 owner 边界，但没有指定如何验证候选入口被删除后原路径仍健康（原文 L8-L10）。
- **影响**：新组合器即使降低某个任务的耗时，也可能遮蔽既有 skill、改变触发优先级、破坏验证或让历史产物无法读取。没有回归和移除证据，团队不能判断失败来自新层还是现有系统，也无法安全停止实验。
- **建议**：在 PoC 前保存安装、skill discovery、触发冲突、验证、文档/roadmap 治理和 Git 安全的基线结果；PoC 后逐项重跑，并加入“完全删除实验入口、临时索引和方案产物后”的复测。把既有任务成功率不得下降、旧方案仍可读取、删除后基线全部通过列为硬门槛；任一不通过，冻结扩展并回退到实验前快照，不修改现有 skill 语义或全局路由。

**观点 4：继续或停止必须由可审计的证据包和预先阈值触发。**

- **发现**：Q4 要求成功阈值、停止条件和回退路径，Q5 要求用指标决定继续、修改或停止（原文 L17-L18）；但文档当前只有问题清单，没有指标定义、观测次数、证据格式或停止触发器。
- **影响**：团队容易用一次端到端演示代替质量证明，或者在指标不完整时继续扩展薄编排层；不同 Agent 也可能用不同口径报告“成功”，导致结果不可复核。
- **建议**：每次 fixture 运行生成证据包，固定记录 fixture 版本、skill 索引版本、输入摘要、方案/运行状态、预期与实际结果、人工决策、失败日志和副作用检查；由脚本汇总而非手工填报。建议继续门槛为：必需字段完整率 100%、代表任务通过率至少 90%、相对当前路径的中位组装时间下降至少 25%、重复运行结果的关键不变式一致率至少 95%，并且未批准写入、authority bypass、回归失败均为 0。任一安全或回归硬门槛失败立即停止；价值指标未达标则保留现状入口并删除实验层，等待修改后的新版本重新跑同一 fixture。

### 视角：S（安全 / 威胁建模）

`视角来源: 跨会话独立Agent`

**观点 1：把整条用户旅程按信任边界拆开

- **发现**：原文 Q1 将旅程定义为“安装 → 发现 → 选择 → 组合 → 执行 → 验证 → 沉淀”，并要求区分 skill 缺口和产品体验缺口（原文 ## 待讨论问题（scope 草案）` Q1）；但文档没有枚举入口、出口、外部内容来源或各阶段的信任边界。
- **影响**：安装时的 skill 内容、发现时的描述/索引、组合时的模型输入都可能携带恶意指令或伪造前置条件。若方案生成器把这些内容当作可信控制数据，攻击者可诱导选择高权限 skill、读取本地信息或把敏感结果写入沉淀产物，形成从内容注入到执行副作用的可达链路。
- **建议**：为七个阶段建立威胁模型，分别标注不可信输入、信任边界、可用权限、数据出口和验证责任。skill 元数据与外部仓库内容默认按不可信数据处理；记录来源、版本、摘要和许可，组合器只生成建议，不把描述文本升级为权限。至少用恶意描述、伪造前置条件和夹带指令三类 fixture 验证路由不会越权。

**观点 2：自动路由会产生混淆代理和权限升级面

- **发现**：原文 Q2 要比较可解释组合器、有限状态薄编排层和强 router/runtime（原文 ## 待讨论问题（scope 草案）` Q2），Q3 又要求明确 Human 决策点和不可逆动作边界（原文 ## 待讨论问题（scope 草案）` Q3）；当前 scope 没有规定自动选择使用什么权限、如何防止推荐结果直接触发高风险能力。
- **影响**：router 若代表用户调用写文件、外部网络、Git 推送或凭据相关 skill，就可能成为混淆代理：用户只批准“生成方案”，运行时却借方案执行更高权限动作。一个被污染的 skill 名称或上下文也可能让路由器绕过原有人工确认，扩大攻击面。
- **建议**：把“推荐”和“执行”分离为不同权限主体；默认路由只读 skill 索引和仓库元数据，执行前必须展示每一步权限、数据范围、外部出口和不可逆动作并获得明确批准。对网络、写入、凭据、发布和 Git push 设为 deny-by-default 的能力标签；任何未声明能力或权限升级都强制阻断并留审计记录。

**观点 3：计划、证据和沉淀产物需要数据最小化与保密边界

- **发现**：原文 Q3 要求定义推荐形态的输入、输出、状态、失败表现和 Human 决策点，Q4 要求验证不产生隐式副作用（原文 ## 待讨论问题（scope 草案）` Q3-Q4）；但文档没有规定任务输入、验证证据、失败日志和沉淀产物中哪些数据可持久化、可供谁读取。
- **影响**：组合方案和验证日志可能复制源码片段、个人数据、凭据路径、内部仓库 URL 或模型上下文；一旦写入共享目录或被后续 skill 读取，泄露面会跨越原任务权限。失败重试还可能把秘密重复写入日志，使删除单个方案包无法完成清除。
- **建议**：在 `Plan`/运行记录契约中加入数据分类、最小化和保留期限字段；默认只保存引用、摘要和脱敏证据，不保存凭据、完整环境变量或不必要源码。敏感字段在生成、日志、验证和沉淀四处统一脱敏；读取和导出需沿用现有 Human/仓库权限。用固定 secret fixture 检查磁盘产物、终端输出和失败日志均无明文泄露。

**观点 4：首个可逆 PoC 必须在受限环境中证明无副作用

- **发现**：原文 Q4 要求最小纵切降低组装成本，同时不产生第二 authority、隐式副作用或 runtime 锁定（原文 ## 待讨论问题（scope 草案）` Q4）；原文没有进一步规定 PoC 的沙箱、网络出口、文件范围、符号链接处理或回滚验证方式。
- **影响**：即使产品入口声称只“生成方案”，解析 skill、执行探测或写入临时文件也可能触发命令、跟随恶意路径或访问任务目录外数据。没有受限环境和完整审计，无法证明失败后不存在残留权限、外连请求或半写入产物。
- **建议**：首个 PoC 采用只读 fixture 仓库和显式 dry-run，禁止 shell、网络、凭据读取、Git 写操作和跨目录文件访问；对路径遍历、符号链接、恶意 Markdown/skill 指令和 prompt injection 做负向测试。记录每次文件、进程和网络尝试；回退验收为删除 PoC 入口后基线可运行、无持久状态、无外连、无未声明文件变更。

**观点 5：安全指标是继续演进的硬门槛，并需支持撤销

- **发现**：原文 Q5 要求用指标决定继续、修改或停止并保留回退路径，成功判据也要求给出成功阈值和停止条件（原文 ## 待讨论问题（scope 草案）` Q5；原文 ## 上下文` 的“成功判据”）；但没有列出安全事件阈值、审计责任、skill 撤销方式或已生成方案的失效策略。
- **影响**：用户组装时间下降可能掩盖一次未授权写入或数据泄露；若没有版本撤销，已污染的 skill 或旧 Plan 仍可能被重复使用。安全事故无法区分局部实验失败与需要冻结整个组合入口的事件，继续演进会扩大影响范围。
- **建议**：把以下条件设为阻断式门槛：未批准的写入/外部调用/权限升级为 0，秘密明文进入产物和日志为 0，审计记录完整率 100%，所有方案均有来源、版本和过期策略。建立 skill/方案撤销清单：来源版本失信、规则变更或发现注入时立即标记不可执行并要求重新生成；任何门槛失败即停止扩大、隔离并删除实验层，保留事件记录供 Human 审核后决定恢复。

## 主力AI 整合立场（主会话，非独立视角，低权重）

`视角来源: 同会话SubAgent(低权重)`

> ⚠ 非独立。以下只作编排摘要，不作为结论权威依据。

- B/C/A/U/T/S 均把主要问题定位为“用户需要从目录中自行完成能力组装”，而不是单纯缺少更多 skill。
- 共同倾向是先做可解释组合方案生成器：输出版本化、可读、可审查、可回退的 Markdown 方案包；执行继续沿用既有 skill、roadmap、证据和 Human 决策。
- 强 router/suite runtime 能降低一次性选择成本，但会引入第二 authority、隐式状态、权限升级和宿主锁定；应作为被拒绝或后续实验选项。
- PoC 必须同时测用户价值、解释性、执行质量、无副作用、回退和删除后的基线恢复。

## conclusion（含沉淀指令）

- **子问题结论：** 推荐 ZAgentic 先演进为“可解释组合方案生成器 + 既有 skill/roadmap 执行”的薄产品形态，而不是直接引入强 router/suite runtime。组合器接收用户目标、约束、权限与证据要求，输出符合其内置版本化模板的 Plan；Human 审查后才进入既有执行链，结果回填证据、验证和可复用记录。若已有 skill 无法覆盖需求但存在可信候选，组合器给出建议；若没有可信建议，必须逐行输出 `required skill：简短地描述缺失skill的形状`，让缺口成为后续 skill 设计或研究输入。
- **解法：**
  1. **输入：** 任务目标、范围/预算/时间约束、可用 skill 偏好、权限边界、验收标准与证据要求。
  2. **输出：** 候选 skill/workflow、选择理由、执行顺序、输入输出契约、Human 检查点、权限/副作用说明、验证命令、失败出口、回退步骤和 provenance；若覆盖不足，附“建议”或逐行 `required skill：<缺失 skill 形状>` 缺口清单。
  3. **模板：** Plan 模板作为组合器 skill 的内置版本化资源，Plan 携带模板版本和来源；模板升级必须显式变更版本，不能静默改变旧 Plan 的含义。
  4. **状态：** `planned → approved → running → blocked/failed → verified → recorded`，另有 `cancelled` 与 `rolled_back`；生成器只拥有 `planned` 方案和解释，不拥有执行权限或长期治理 authority。
  5. **Human 决策点：** 批准方案、批准高风险能力、处理冲突/过期依赖、接受验证结果、决定是否固化经验。
  6. **最小纵切 PoC：** 选择“外部仓库研究”和“一套工具组合设计”两个真实任务，与当前人工组装基线对照；只写入 `skills-outputs/` 下版本化方案包，不改 skill 定义、不自动执行不可逆动作。
  7. **继续阈值：** 首次生成有效方案时间相对基线下降 ≥30%；独立用户能解释选择理由的比例 ≥80%；执行成功率不低于基线；零 authority bypass、零未声明副作用；删除生成器后原有路径可复现。任一高风险副作用、权限绕过、持续性 runtime 依赖或基线回归超过 20% 即停止并删除适配层。
