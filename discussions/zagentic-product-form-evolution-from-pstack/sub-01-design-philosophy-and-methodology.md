# 设计哲学与方法论：pstack-claude 对比 ZAgentic

> 本文件对应 MASTER 索引中的第一项，按“一事一议”原则独立讨论与求解，由 `zj-discuss` + `zj-discuss-view` 维护。

## 上下文

- **所属主文档：** [../MASTER.md](./MASTER.md)
- **本子问题独立性：** 本文只比较两个项目的设计哲学、方法论、自治与治理假设，以及可迁移/不可迁移边界；这些判断可直接依据固定版本技术报告、capability-fit 记录与 ZAgentic 当前治理文档完成，不依赖目标产品子文档先下结论。
- **成功判据：** 形成统一维度比较矩阵；事实、解释和价值判断分开；每个优点说明适用条件、每个缺点说明实际后果；产出 3–7 条设计张力和“可借鉴机制 / 不可迁移假设”清单，但不决定 ZAgentic 最终产品形态。
- **声明必需角色集：** B,C,A,R

## 待讨论问题（scope 草案）

- Q1：两个项目分别把什么视为基本产品单元：skill、workflow、router、suite，还是决策与证据协议？
- Q2：两者如何处理发现、路由、组合、执行、验证、复盘和经验固化？
- Q3：两者对自治、Human authority、状态、运行时、宿主适配和退出路径有哪些不同假设？
- Q4：各方法在速度、科学性、可组合性、可理解性、可维护性和认知负担上的收益与代价是什么？
- Q5：哪些 pstack 机制属于可迁移原则，哪些与其宿主/runtime 不可分？

## Agent viewpoints（独立视角 — 须跨会话独立 Agent）

> 每个视角必须由声明角色的独立 Agent `Read` 本文件原文后撰写；每个观点块都要带“发现 / 影响 / 建议”和原文定位。

### 视角：B（技术经理 / 可落地）

`视角来源: 跨会话独立Agent`

**观点 1：先把比较结果做成可验收的交付物

- **发现**：原文成功判据要求“形成统一维度比较矩阵”、区分事实/解释/价值判断，并产出 3–7 条设计张力及可迁移清单（原文 L8-L10）；但没有规定矩阵必须覆盖哪些字段、谁负责补齐、何种状态算完成，也没有成本或工期口径。
- **影响**：团队可以按时写出一篇信息完整的比较文章，却无法判断 Q1–Q5 是否都已回答，或判断一个机制是否已经足够成熟可以进入后续产品讨论；这会把返工推迟到子文档 2，增加跨文档依赖和排期不确定性。
- **建议**：在本子文档的整合阶段固定一张验收表，至少包含“基本单元、生命周期环节、自治/权限假设、宿主依赖、收益、实际代价、迁移分类、证据来源、责任角色、完成状态”字段。每个 Q1–Q5 至少有一行结论；每条设计张力必须写适用条件和实际后果；B 以“字段无空缺且 3–7 条张力均有证据”作为本阶段完成门槛。

**观点 2：显式管理从比较到产品决策的依赖链

- **发现**：原文明确限定本子问题“只比较”而“不决定 ZAgentic 最终产品形态”（原文 L8-L9），结论区也再次声明“本文不提前决定 ZAgentic 最终产品形态”（原文 L71-L74）；同时 Human 对 B、C、A、R 四轮拍板均为“待拍板”（原文 L62-L69）。
- **影响**：这形成了一个有意的边界，但当前没有写出本子文档向目标产品子文档的交付接口。若没有明确的 handoff，子文档 2 可能重新解释同一批事实，或者在缺少角色拍板时直接把比较意见当成产品承诺，造成重复劳动和决策越权。
- **建议**：在合成前建立一份跨文档 handoff：列出已确认的比较事实、待 Human 决策的问题、不得直接迁移的假设，以及每项结论进入子文档 2 的输入位置。排期按“角色观点完成 → Human 拍板 → 本文矩阵封版 → 子文档 2 选型”顺序执行；只有前一步的验收表通过，下一步才启动。若 Human 未拍板，结论状态保持 `NEEDS_CONTEXT`，不得标记为产品路线。

**观点 3：对可迁移机制设置成本、依赖和回退闸门

- **发现**：待讨论问题同时覆盖发现、路由、组合、执行、验证、复盘、经验固化（原文 L14-L15），以及自治、Human authority、状态、运行时、宿主适配和退出路径（原文 L16-L18）；成功判据只要求列出“可借鉴机制 / 不可迁移假设”，没有要求给出迁移代价、依赖链、风险或回退方案（原文 L8-L9）。
- **影响**：如果只从概念相似性判断“可借鉴”，团队很容易把 pstack 的宿主 runtime、权限假设或状态管理一起带入 ZAgentic。后续一旦发现不兼容，撤回成本会高于在比较阶段做分类；这也是最可能把研究工作膨胀成隐性重构的路径。
- **建议**：对每个候选机制强制补充四个执行字段：依赖（skill、runtime、权限、宿主）、投入量级（S/M/L，并说明关键工作）、风险与触发条件、回退动作。只允许三种落地状态：可直接迁移、需薄适配后验证、拒绝迁移；进入“需适配”必须有最小验证场景和删除适配层的回退路径，进入“拒绝”必须记录阻断原因。

**观点 4：控制角色协作的产出边界，避免多轮讨论变成无界调研

- **发现**：原文要求由独立 Agent 完成角色观点，并规定每个观点必须带“发现 / 影响 / 建议”和原文定位（原文 L20-L22）；角色集只有 B、C、A、R（原文 L9-L10），但没有限制每个角色的观点数量、重复判定或整合时的冲突处理方式。
- **影响**：独立性提高了覆盖面，却也会产生重复证据和相互冲突的建议；如果没有统一的退出条件，角色轮次可能持续增加，技术经理无法确认什么时候可以封版，也无法估算后续 Human 拍板的工作量。
- **建议**：每个角色限定 3–5 个观点，观点必须映射到 Q1–Q5 中至少一个问题且不得重复同一发现；整合时把冲突分成“事实冲突、优先级冲突、风险容忍度冲突”，分别交给证据补充、Human 取舍或架构约束处理。所有角色区块完成、冲突有归属、验收表无空缺后停止新增角色和调研。

### 视角：C（产品专家 / 用户价值·生态竞品）

`视角来源: 跨会话独立Agent`

**观点 1**

- **发现**：原文 ## 上下文` 的成功判据要求形成“统一维度比较矩阵”，而 `## 待讨论问题（scope 草案）` Q1 同时把 skill、workflow、router、suite、决策与证据协议列为候选基本产品单元；目前没有说明哪一类用户在什么任务中购买或采用哪一个单元。
- **影响**：价值主张会停留在内部分类学层面，用户无法判断“我现在要解决的问题应该选一个 skill、一个 workflow，还是一套组合”。这会直接增加首次使用的选择成本，也使 pstack-claude 与 ZAgentic 的差异无法用一个可验证的采用理由表达。
- **建议**：为每类候选产品单元补一张面向用户的 job card：目标用户、触发任务、输入、可见产出、替代方案和退出条件；至少用“研究一个外部仓库”和“设计并验证一套工具组合”两个任务验收，记录首次选型时间、任务完成率和用户能否解释选择理由。

**观点 2**

- **发现**：原文 ## 上下文` 的成功判据列出速度、科学性、可组合性、可理解性、可维护性和认知负担六个价值维度，并要求说明优点的适用条件、缺点的实际后果；但 `## 待讨论问题（scope 草案）` Q4 没有给出目标用户、竞品参照或六个维度之间的优先级。
- **影响**：比较很容易变成“每项都不错”的静态评审，无法回答用户为何在真实场景中选择 ZAgentic 而不是 pstack-claude 或手工流程；吸收机制时也可能为了覆盖维度而增加运行时、路由和治理复杂度，反而提高认知负担。
- **建议**：建立按用户任务切片的竞品证据矩阵，至少覆盖新用户、熟悉 skill 的开发者和维护者三类角色；为每个任务只指定一至两个首要价值指标，并预先写出可证伪阈值，例如“新用户在限定时间内能生成并解释组合方案”“维护者能定位一次失败是路由、执行还是验证问题”。没有达到阈值的机制不进入产品主路径。

**观点 3**

- **发现**：原文 ## 待讨论问题（scope 草案）` Q2 要求比较发现、路由、组合、执行、验证、复盘和经验固化，Q5 又要求区分可迁移原则与不可迁移的宿主假设；但文档没有把用户从首次安装到重复使用、贡献 skill 以及处理失败的完整生命周期定义出来。
- **影响**：即使一次组合任务成功，用户仍可能不知道如何复用成果、何时反馈失败、何时升级或替换 skill；生态侧也无法形成“使用结果反哺 skill 质量”的闭环。产品会更像可浏览的技能集合，而不是能降低下一次决策成本的能力系统。
- **建议**：把“发现 → 组合 → 执行 → 验证 → 复盘 → 固化”定义为一个可回访的用户闭环，并为每一段规定用户可见的产物和失败出口：组合方案、证据包、验证结果、复盘记录和可复用条目。PoC 至少跟踪首次成功时间、同一用户第二次复用率、失败后恢复率，以及新增条目是否能被另一位用户解释和复用；这些指标不成立时，不扩大 router 或 suite 的产品承诺。

### 视角：A（架构师 / 约束）

`视角来源: 跨会话独立Agent`

**观点 1：先固定产品单元与 authority，再讨论路由。**

- **发现**：原文 ## 待讨论问题（scope 草案）/ Q1` 同时列出 skill、workflow、router、suite 与“决策与证据协议”，但没有声明它们之间的层级关系或谁拥有最终语义；原文 ## 上下文 / 成功判据` 又要求形成统一维度比较矩阵，说明产品单元和比较维度仍待定义。
- **影响**：若把 router 或 suite 当成与 skill 同级的产品单元，后续会出现重复编排语义和第二 authority；组合结果可能绕过现有 skill discovery、evidence、roadmap 与 Human 决策边界，向后兼容只能靠隐式约定维持。
- **建议**：在比较矩阵中增加“语义 owner、可持久化状态、调用入口、退出路径、版本兼容策略”五列，并先写一条不变式：skill/工作流定义能力，决策与证据协议定义可审计事实，任意新 router 只能生成建议或受限执行计划，不能取代现有 authority。用一条现有任务链验证该契约后，再决定是否需要 suite 层。

**观点 2：自治边界必须以状态机和回滚契约表达。**

- **发现**：原文 ## 待讨论问题（scope 草案）/ Q3` 明确要求比较自治、Human authority、状态、运行时、宿主适配和退出路径；原文 ## 上下文 / 成功判据` 要求每个优点说明适用条件、每个缺点说明实际后果，但没有为“暂停、拒绝、失败、恢复”定义共同状态。
- **影响**：只比较“自动化程度”会漏掉最危险的兼容性问题：同一工作流在不同宿主上可能对 Human authority 的解释不同，失败后也无法判断哪些副作用已经发生。没有显式状态和退出契约，任何未来编排层都会把临时运行上下文变成不可迁移的隐式状态。
- **建议**：为两项目统一抽象最小生命周期：`planned → approved → running → blocked/failed → verified → recorded`，另设明确的 `cancelled` 和 `rolled_back` 条件；每个状态标注 owner、允许的副作用、人工决策点和恢复输入。比较 pstack 机制时，只迁移可映射到该生命周期的部分，宿主特有的全局 router、hooks 或 transcript 状态列入不可迁移假设。

**观点 3：组合接口应保持窄而稳定，避免过早引入 runtime 耦合。**

- **发现**：原文 ## 待讨论问题（scope 草案）/ Q2` 要求比较发现、路由、组合、执行、验证、复盘和经验固化的全链路；`/ Q5` 又要求区分 pstack 的可迁移原则与“与其宿主/runtime 不可分”的假设。这把跨系统接口稳定性和宿主耦合列为直接评估对象。
- **影响**：如果把 pstack 的执行 runtime 作为组合接口，skill 会依赖特定命令、会话、hook 或模型选择机制，迁移成本随 skill 数量线性甚至超线性增长；若只复制文字模板，又会丢失验证和复盘契约，形成看似可组合、实际不可验收的浅层集成。
- **建议**：将可迁移边界收敛为版本化的输入/输出协议：输入含目标、约束、证据要求和权限；输出含计划、证据引用、验证结果、未决风险和下一步。runtime 只实现协议适配器，不进入 skill 的核心语义；为至少一个 pstack 工作流做“原宿主→ZAgentic 协议→人工执行”的双向映射测试，失败时保留原 skill 路径。

**观点 4：比较矩阵必须显式记录长期一致性与兼容代价。**

- **发现**：原文 ## 上下文 / 成功判据` 要求统一维度比较，并列出速度、科学性、可组合性、可理解性、可维护性和认知负担；但原文 ## 待讨论问题 / Q4` 的维度没有包含版本演进、迁移、删除或回退成本，`/ Q5` 才概括性地提出可迁移/不可迁移边界。
- **影响**：一个机制可能短期提升速度和可组合性，却把协议版本、文档索引和历史产物锁在 pstack 的约定上；若矩阵没有兼容与迁移列，吸收决策会系统性低估未来删除旧 router、重写 skill 或恢复旧产物的成本。
- **建议**：在统一矩阵中增加“契约版本、升级/降级路径、迁移脚本或人工步骤、删除成本、回退可行性”列，并为每项候选机制设定兼容闸门：能否在没有新 runtime 的情况下继续执行、能否读取旧产物、能否只撤销新增层而保留原 skill。未满足者只能列为实验性适配，不进入默认产品路径。

**观点 5：把治理与经验固化作为跨项目边界，防止组合层变成第二知识库。**

- **发现**：原文 ## 待讨论问题 / Q2` 将“复盘和经验固化”与发现、执行、验证并列；原文 ## 上下文 / 本子问题独立性` 指定判断可依据技术报告、capability-fit 记录与 ZAgentic 当前治理文档完成，并明确本子文档不决定最终产品形态。
- **影响**：若 pstack 的复盘笔记、模型选择或运行日志直接成为新的长期知识源，ZAgentic 会形成两套互相漂移的规则；后续产品形态讨论也会把过程性讨论误当成长期 authority，违背本子文档与治理文档的职责边界。
- **建议**：把经验固化拆成“过程记录”和“治理沉淀”两步：组合层只能产出带来源、版本和验证状态的候选记录；经 Human/治理流程确认后，才回填 skill、ADR、路线图或 ZJ-CONTEXT.md。对每个迁移机制定义唯一落点和淘汰规则，并在比较结论中列出不可进入长期 authority 的临时产物。

### 视角：R（学术 / 研究严谨）

`视角来源: 跨会话独立Agent`

**观点 1：先把“基本产品单元”变成可操作的分类

- **发现**：**事实**是 Q1 同时列出 skill、workflow、router、suite，以及“决策与证据协议”，但原文没有给出这些术语的判定属性、层级关系或可观测边界（原文 ## 待讨论问题（scope 草案）` Q1）。**解释**是这些候选处于不同抽象层：把它们直接放进同一比较矩阵，可能把“能力载体”“运行编排器”和“治理协议”混作同类变量。**价值判断**因此只能暂缓，当前材料不足以断言哪一种是更好的基本单元。
- **影响**：比较结果的可复现性会受分类者先验影响；两个研究者可能对同一机制给出不同单元标签，随后在可组合性、维护成本等指标上得到不可比结论。若不先定义分类，Q1 的结论不能作为产品路线的证据。
- **建议**：建立一个预注册式分类表，为每个候选单元固定“输入、输出、状态、调用者、语义 owner、权限边界、持久化位置、退出路径”字段，并规定一项机制可同时拥有主类和辅助类但必须说明理由。用技术报告固定版本中的代表性 skill/workflow 各抽样一项，由两名独立评审按表分类，记录分歧并在整合前解决；报告分类规则、样本和未覆盖项，避免把解释写成事实。

**观点 2：生命周期比较需要可重放的证据链

- **发现**：**事实**是 Q2 要求覆盖“发现、路由、组合、执行、验证、复盘和经验固化”（原文 ## 待讨论问题（scope 草案）` Q2）；但原文没有规定每个环节的输入/输出格式、成功与失败事件、观察者可见性或重放步骤。**解释**是当前 scope 允许用叙述性描述代替过程证据。**价值判断**是这种描述可以帮助理解，但不足以支持方法优劣的因果判断。
- **影响**：无法区分某个机制本身的效果与操作者熟练度、任务难度、模型或宿主差异带来的混淆；第三方也不能从相同输入重跑“为何路由到此、验证是否通过、经验如何固化”。这会使“科学性”和“可维护性”的比较停留在印象层面。
- **建议**：为七个环节建立统一事件账本：每条记录至少含任务 ID、固定版本、输入约束、候选/选择、人工决策、产出、证据引用、失败原因和下一状态。选择两个代表任务进行端到端重放，保存原始输入、执行日志和验证结果；若某环节只能依赖人工判断，明确标为未观测变量，不把推断写成已验证机制。

**观点 3：自治与宿主依赖必须采用同一操作定义

- **发现**：**事实**是 Q3 明确要求比较“自治、Human authority、状态、运行时、宿主适配和退出路径”（原文 ## 待讨论问题（scope 草案）` Q3）；但原文没有定义自治等级、人工批准发生在哪些状态、哪些副作用可逆，也没有列出跨宿主的控制变量。**解释**是“更自治”可能只是把人工步骤隐藏在特定 runtime 中，而不是能力真的更强。**价值判断**因此不能仅依据自动步骤数量评价两项目。
- **影响**：相同工作流在不同宿主上的权限和退出语义可能不同，导致自治、风险和迁移性的结论不可外推；若不记录未执行的副作用，失败后也无法判断恢复成本。任何关于“pstack 原则可迁移”的结论都可能把宿主特例误当成通用原则。
- **建议**：预先定义自治测量：自动选择、自动执行、自动验证和自动固化分别计数，并为每步记录人工批准点、权限、可逆性和停止条件。以相同任务、相同输入约束和相同证据要求，在原宿主与 ZAgentic 可用的执行环境中做对照；无法保持控制变量时，降低结论置信度并明确标注“仅适用于该宿主”，不得外推。

**观点 4：六个评价维度需要基线、指标和权重

- **发现**：**事实**是成功判据列出速度、科学性、可组合性、可理解性、可维护性和认知负担，并要求说明优点的适用条件、缺点的实际后果（原文 ## 上下文` 的“成功判据”）；但原文没有给出基线、测量单位、任务样本、维度权重或停止规则。**解释**是“统一维度”目前只保证覆盖面，不保证不同方案的数值或证据可比。**价值判断**是任何综合优劣排序在此阶段都应视为暂定意见，而非研究结论。
- **影响**：一个方案可以用速度优势抵消维护代价，也可以因研究者主观偏好得到相反排序；没有基线就无法知道改进是否超过自然波动，没有权重就无法解释为何某个 trade-off 被接受。结果难以复核，也不能直接支撑第二子文档的产品选择。
- **建议**：在研究开始前固定最小评价协议：当前 ZAgentic 流程为基线，选定至少两个任务样本；速度用完成时间/人工介入次数，科学性用证据完整率/可重放率，可理解性用独立用户解释成功率，维护性用变更面和回归数量，认知负担用选择步骤和未决问题数。权重由 Human 在合成前确认；没有足够样本的维度只报告定性证据和置信度，不生成总分。

**观点 5：可迁移性必须由失败可证伪的判定规则支持

- **发现**：**事实**是 Q5 要求区分“可迁移原则”与“与其宿主/runtime 不可分”的假设（原文 ## 待讨论问题（scope 草案）` Q5），成功判据也要求产出“可借鉴机制 / 不可迁移假设”清单（原文 ## 上下文` 的“成功判据”）；但原文没有定义“不可分”的证据阈值、依赖清单格式或失败测试。**解释**是当前分类容易依赖研究者的直觉：概念上相似的模板可能仍隐含命令、权限、状态或模型选择依赖。**价值判断**是“可迁移”只有在给出反例和回退路径后才足以指导吸收。
- **影响**：分类结果难以被第三方复核，也容易把迁移成本推迟到实现阶段；若迁移失败后没有回退，研究本身可能诱发不可逆的运行时耦合。对 ZAgentic 的长期治理而言，这会把一次性实验误写成稳定能力。
- **建议**：为每项候选机制建立迁移试验卡：依赖（命令、权限、状态、模型、宿主）、协议输入/输出、最小替代适配器、两类失败注入、验证证据和删除/回退步骤。只有在不引入第二 authority、能在人工执行路径中完成、且失败可回退时标为“可迁移”；否则标为“需适配”或“不可迁移”，同时记录证据版本、反例和结论置信度。整合时把事实、解释、价值判断分栏，避免把试验性分类固化为长期规范。

## conclusion（含沉淀指令）

- **子问题结论：** 两项目都把“阶段化任务推进 + 可验证产出”作为复利来源，但产品单元和 authority 不同：pstack 以 suite/router 驱动连续执行，ZAgentic 以可拆卸 skill、证据协议和 Human 治理维持长期可组合性。pstack 的阶段化方法、验收契约、证据包和复盘记录可作为薄层原则；其全局 router、宿主运行时、hooks、模型/转录状态和 shipping glue 不应直接成为 ZAgentic 的第二 authority/runtime。本文采用的产品单元边界是：组合器负责从能力目录生成建议和 Plan，能力缺口无可靠建议时逐行输出 `required skill：<缺失 skill 形状>`；Plan 的模板由组合器 skill 内置并版本化。
