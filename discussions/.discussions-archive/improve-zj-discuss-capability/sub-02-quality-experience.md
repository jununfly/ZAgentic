### 视角：B（技术经理 / 可落地）
`视角来源: 跨会话独立Agent`

**观点 1** — Q1 bug1 根因是「准备阶段无强制工具」，修复应复用已有解析器而非加新自觉约定
- 发现：原文 Q1 已定位根因——"准备阶段 AI 只列出可选角色 key…却未带出 role-matrix.md 的「一句话简介」…根因 = 该步靠 AI 自觉，无强制"（原文 L16-18）。而 SKILL.md 的准备阶段本就要求"推荐参与角色每个带一句话简介 + 推荐理由、其他可选角色每个也带一句话简介"（原文 SKILL.md L64-69；role-matrix L69-75）。launch_pack.py 的 `load_role_pool` 已从 role-matrix 解析出 key→intro（原文 launch_pack.py L54-81，PACK_TEMPLATE 在 L94 带出 intro），说明 intro 数据现成、解析逻辑已存在，唯独没在"准备阶段"这一步被调用。
- 影响：根因不是缺数据，而是准备阶段的角色清单是 AI 自由文本、无机械出口。该自由文本环节是整条链路唯一没有工具强制的节点，故 bug 必然复发；修"自觉"无效。落地代价低——复用 `load_role_pool` 新增一个只读子命令（约 40 行、0.5 人日）即可消除该环节，而不是重写流程或新增数据源。
- 建议：在 launch_pack.py 增加 `--prep [--signals T,S,O…]` 子命令，输出"推荐角色（base+命中信号）"与"其他可选角色"两套清单，每条强制带 `key / 一句话简介 / 推荐理由（命中信号或 base）`，直接照搬 `load_role_pool` 解析结果。把 SKILL.md L64-69 从"AI 应呈现"改写为"必须运行 `python3 launch_pack.py --prep` 并原样粘贴其输出"，使准备阶段与 launch pack 共用同一数据源（role-matrix），消除"AI 自觉"缺口。验收：跑 `--prep` 输出含每角色 intro 且 SKILL 指引改为脚本驱动；不新增独立数据源。

**观点 2** — Q2 证据闸门正则过窄会误伤「以章节定位」的有效观点，制造摩擦
- 发现：check_subdoc.py 的证据判定正则为 `EVIDENCE_RE = 原文\s*[L（(]`（原文 check_subdoc.py L67），只接受"原文 Lxx"或"原文（…）"两类定位符。但 B gated method 只要求"发现字段须能回溯到 Read 到的原文"（原文 role-methods/B.md L32-33），示例为"如 原文 Lxx"，并未禁止以章节名定位。实际写作中大量有效观点会以"原文 ## 上下文 / 原文 §结论不变式"定位，这类写法会被 L67 正则判定为无证据、直接拒收。
- 影响：这是会真实发生的误伤（正则仅认 L/（ ，不认 # 章节）。后果：跨会话独立 Agent 写出的有效观点被闸门退回，制造摩擦、拖慢收敛；更糟的是可能逼写作者"编造行号"以通过，反而损害证据真实性。量化：当前正则字符集 `L（(` 仅 3 个开头，覆盖不了 `原文 ##`/`原文 §` 等常见形式。
- 建议：将 EVIDENCE_RE 放宽为接受章节锚点，例如 `原文\s*[#L§（(]`（追加 `#` 与 `§`，并允许 `原文：## 上下文` 前缀），或改为"原文"后跟任意非空白定位串即命中（`原文\s*[^\s，。]+`）。同步把 role-methods 各文件与 sub-02 模板的"证据定位"措辞统一为"行号或章节锚点均可"。验收：check_subdoc.py 对"原文 ## 待讨论问题"类引用返回 0 violation；补一条 tests 用例覆盖章节锚点。做到什么程度算完 = 闸门放行所有"能回溯原文"的合理定位形式。

**观点 3** — Q3 处置闭环存在「结论可过闸门却沉淀指令为空」的断点，需把沉淀指令纳入机械校验
- 发现：子文档 conclusion 模板要求"沉淀指令：改哪些 PRD/ADR/文档、跨子文档约束登记、待删临时脚手架"（原文 sub-02 L85-88），但 check_subdoc.py 的 conclusion 校验只查三件事：状态协议枚举合法（L110-122）、不引用同会话预演为权威（L123-133）、非降级锚点（L228-248）。没有任何一项强制"沉淀指令"段非空、或"待删临时脚手架"有交代。Phase 4 处置契约写明"invoke zj-docs-ontology 分类…Human 确认后删除"（原文 SKILL.md L140-144），且 sibling-boundary 限定"discuss 不得运行 docs_governance.py、不得决定最终分类"（原文 SKILL.md L281-282），即真实删除依赖外部 zj-docs-ontology + 人类确认两步。
- 影响：当前闸门允许"状态协议=DONE 但沉淀指令全空"的子文档通过，而硬规则 5 明确要求结论必须含可执行沉淀指令否则不算闭环（原文 SKILL.md L242-244），check_subdoc 并未机械执行这条。这是真实闭环断点：过程噪音（briefings/、launchpack、草稿，原文 sub-02 L63-67 已标"删除候选"）可能因结论无删除指令而残留，违背 Phase 2 清理纪律。依赖面：闭环卡在 zj-docs-ontology 可用性 + 人类确认两步，任一步缺失都应使状态落到 BLOCKED/NEEDS_CONTEXT 而非 DONE。
- 建议：扩展 check_subdoc 第 3 类校验，要求 conclusion 含 `沉淀指令` 段且至少 1 条非空项（列出改的文档路径或待删临时物）；缺失即 violation（非降级断点）。把"若 zj-docs-ontology 未跑/未 Human 确认，不得标 DONE"写成 MASTER/子文档处置契约的硬前提，由主力 AI 在合成时显式判状态。验收：沉淀指令为空的 DONE 结论被 check_subdoc 判为 1 violation；补 tests 用例。做到什么程度算完 = 闸门与硬规则 5 对齐，杜绝"空结论通过"。

**观点 4** — Q2 launch pack 粘贴链路与临时脚手架删除职责已规划，但缺「谁在 Phase 2 收尾登记」的显式归属
- 发现：sub-02 已声明"视角 briefing（临时脚手架，阶段 2 删除候选）"（原文 sub-02 L63-67），conclusion 模板也留了"待删临时脚手架"字段（原文 sub-02 L88），说明删除意图存在。但 SKILL.md 的 Phase 2/3 收敛与 Phase 4 处置之间，没有一句话明确"收尾删除动作由谁触发、在哪个步骤把 briefings/ 纳入待删清单"——Prepare 阶段的 briefings 由 launch_pack.py 生成（原文 SKILL.md L87-101），而 Phase 4 才谈删除（L140-144）；中间 Phase 3 合成阶段未提及如何把已生成的临时物挂接进处置登记。
- 影响：可落地风险 = 临时物（briefings/*.md、草稿视角）在讨论进行中持续增多，若没有"生成即登记删除"的机制，Phase 4 人类拍板删除时容易遗漏或根本没人知道要删。量化：一个 4 角色子文档会生成 ≥4 个 launchpack + 1 个 briefing 目录，纯靠记忆清干净不现实。这与"做到什么程度算完"直接相关——闭环不仅指结论写定，还包括临时物归零。
- 建议：在 launch_pack.py 生成时，于子文档末尾"待删临时脚手架"或独立 `## 临时物登记` 段追加一行（脚本已写文件，顺手登记成本近 0）；Phase 4 处置前由主力 AI 用 check_subdoc 外的清单核对这些路径是否仍存在，存在且未 Human 确认则状态不得 DONE。明确归属：临时物删除 = "Phase 4 由主力 AI 调 zj-docs-ontology 后、人类确认删除"统一负责，写入 MASTER 处置契约。验收：跑 launch_pack 后子文档出现可机读的待删登记行；Phase 4 缺登记或登记物未删时状态判 BLOCKED。

### 视角：C（产品专家 / 用户价值·生态竞品）
`视角来源: 跨会话独立Agent`

**观点 1** — Q1 bug1：准备阶段角色简介缺失，根因是“AI 自觉”而非工具强制
- 发现：原文 L16-18 明确写准备阶段“只列出可选角色 key（T/S/D/L/F/U/R/P/E）却未带出 role-matrix.md 的一句话简介”，并把根因归为“该步靠 AI 自觉，无强制”。但 role-matrix.md L69-76 早已规定准备阶段“每个角色带一句话简介 + 推荐理由”——即规范早已要求、运行期却没机械保证，存在“规范说要做 / 生成路径没强制”的裂缝。而 launch_pack 生成器（launchpack-C.md L11-12）已能从 role-matrix 程序化带出 intro，说明单一数据源现成可用。
- 影响：准备阶段是用户（Human 发起者）对 zj-discuss 的冷启动第一屏。能否一次性看清“该加哪个角色”直接决定他是否继续用；这步卡住，整场讨论采纳率归零。当前它依赖某个 AI 会话“记得带简介”——这正是已被观察到的真实摩擦点（非想象需求），优先级应按“采纳漏斗第一关”对待。
- 建议：不要走“提示 AI 记得带简介”的回头路（正是它失效）。把准备阶段清单改成与 launch_pack 共用同一条程序化路径——从 role-matrix 的「一句话简介」列直接生成，单一数据源、不靠自觉。验收：新增/跑通一个 prep-list 生成函数（复用 role-matrix 解析），使任何会话产出的准备清单都天然含 intro；并可让 check_subdoc 加一条不变式校验准备清单段含 intro 引用。优先级：高（直接卡采纳）。

**观点 2** — Q2 质量护栏：价值在“不被绕过”，当前最大体验风险是误伤与粘贴链路摩擦
- 发现：原文 L19-21 把 check_subdoc.py 四不变式、状态协议枚举、launch pack 粘贴链路、--all、错误提示一并列为“是否清晰/误伤/friction”待判项。读 check_subdoc.py 可知证据闸门用正则 `原文\s*[L（(`（L67）判定“带原文证据”，且结论不得与预演同句出现依赖词（L123-133）；SKILL L205-210 自述担心“狼来了的闸门会被关掉”。另 SKILL L105-111 解释 `--role X,Y` 已关闭、`--all` 是替代，但仍需 Human 为每个角色各开一次独立会话。
- 影响：护栏的真实用户是编排者/CI。对内部工具，护栏若产生“我觉得没问题却被拒”的误伤（如证据写法不同就被判缺引用），人会关掉脚本——这是 SKILL 自己预警的失效模式，比“漏检”更致命。另一方面粘贴链路：一个 4 角色子文档 = 4 次人工复制+开会话；复杂问题可能数十次往返，是 solo 用户最大的隐性体验成本；`--all` 已缓解但没消除。
- 建议：① 先保护栏正确性：在 tests/ 加“合法但异形证据写法”用例（如「见原文第96行」「（L9-13）」），把 EVIDENCE_RE 放宽到覆盖常见引用，并监控真实拒报率，目标误伤=0，避免闸门被关。② 粘贴链路摩擦不消除隔离（隔离即价值），但应量化采纳损耗：借 metrics.py 已有的 R4 注册表，记录每角色“生成→开会话→结论”的耗时与弃用率，作为体验基线。优先级：中（护栏正确性先于减摩擦）。

**观点 3** — Q3 处置闭环：删除不可逆 + 分类职责断点是两个用户信任风险
- 发现：原文 L22-23 问 Phase 2 调 zj-docs-ontology“分类沉淀、Human 确认后删除”是否顺畅、有无断点（如分类职责、删除前确认）。SKILL L39-42 / L140-144 与 L281-282 规定：discuss 阶段 2 “只吐指针”，分类/迁移/权威校验由 ontology 的 Human 确认闭环完成，discuss 不得运行 docs_governance.py、不得决定最终分类。即“谁真正分类”在 discuss 与 ontology 边界上有交接缝；而删除是“确认后即删文件夹”，不可逆。
- 影响：对收尾决策人（用户），一次确认的硬删除没有回收站 = 点错即永久丢失 durable 结论，是信任红线；若 ontology 没被调用或 Human 没接住，文件夹要么滞留（噪声堆积）要么误删（丢结论），闭环开天窗。断点会直接削弱 Phase 2“沉淀而非丢失”的承诺。
- 建议：① 删除改为“暂存/归档 + 回收窗口”而非硬删：确认后先移到 trash/归档区、保留可恢复，给人后悔期。② 在 conclusion 沉淀指令里补显式交接清单：已沉淀到 docs/ 的哪页、由谁（Human+ontology）确认、discuss 侧交付的指针路径，使“分类职责”不悬空。验收：MASTER 处置契约段加“归档而非删除 + 交接清单”两行硬约束。优先级：中高（不可逆操作必须有后悔机制）。

### 视角：A（架构师 / 约束）
`视角来源: 跨会话独立Agent`

**观点 1** — Q1 bug1 的真正根因不在"缺强制"，而在「准备阶段清单」与 SSOT 是两条数据通路，修复须消除这条分叉
- 发现：原文把根因写作"该步靠 AI 自觉，无强制"（原文 L17），并承认 launch_pack 启动包已带 intro（原文 L17 末句）。但 role-matrix.md 早在 L69-73 就规定准备阶段"每个角色带一句话简介 + 推荐理由"——约束已写进规范，只是没落到可执行层。关键缺口是：启动包走 `launch_pack.py` 的 `load_role_pool`（launch_pack.py L54-81，L94 渲染 `{{intro}}`），而准备阶段推荐清单是 lead AI 的自由文本，二者没有共享对 role-matrix 的读取。两条通路 = 同一份简介可能漂移成两份真相。
- 影响：若只加一句"请 AI 务必带简介"的提示词，等于在分叉的第二条通路上再贴一层自觉，根因未除、必复发。更隐蔽的耦合风险：check_subdoc 四不变式（SKILL L196-210）只校验"视角块内容 + 来源标注"，完全不校验"准备阶段推荐了哪些角色、是否带简介"（原文 L16 的可选 key 与结论覆盖是独立逻辑），所以漏带简介不会触发任何闸门——错误对质量护栏隐形。量化：当前准备阶段简介强制率 0%（纯 prose），且护栏对该失效 0% 可见。
- 建议：把准备阶段角色清单渲染与 `launch_pack.py` 的 `load_role_pool` 合并为单一读取 role-matrix 的入口，准备阶段输出强制为 `key / 一句话简介 / 推荐理由` 三段（理由来自 base 或命中信号，复用 role-matrix L54-67 的映射）；新增回归测试断言 role-matrix 每个 key 的 intro 单元格非空（空则报错而非静默）。自定义角色（`--allow-custom`，launch_pack.py L191-169 拒绝逻辑）intro 为空时显式标注"（自定义角色，无矩阵简介）"而非崩溃。验收：准备阶段与启动包产出同源、无简介缺失；护栏对"声明集与简介完整性"有机器校验兜底。

**观点 2** — Q2 引用不变式与证据闸门各有一处可被拆行/换写法绕过的泄漏，冲击硬规则 3(b) 权威红线
- 发现：check_subdoc.py 对"结论不得引用同会话预演为权威"的判定是"同一行内同时出现 PREVIEW_TOKEN 与 RELIANCE_CUE"（check_subdoc.py L123-133；SKILL L202-205 同述）。这是单行启发式而非结构化解析。证据闸门 `EVIDENCE_RE = 原文\s*[L（(]`（check_subdoc.py L67）只认 `原文 L/（/(`，写成"见 role-matrix 第 96 行"或"依据上述同会话产出"跨行拆开即漏判或误杀。另：gate 只数带证据块数，并不校验观点是否真回答了 Q1/Q2/Q3——而 sub-02 明确要求"回答 Q1/Q2/…"（原文 L33），此实质不变式无机器校验。

**观点 3** — Q2 `--all` 链路自洽，但"非降级锚点"信任基底是 Agent 自证，不是隔离验证，须显式记为边界
- 发现：SKILL L105-111 已正式关闭 `--role X,Y`、把 `--all` 定为唯一合规替代（输出独立启动行），launch_pack.py L31 用 `声明必需角色集` 正则解析本子文档 L12 的 `B,C,A,O`，链路自洽无 usability 缺口。但 check_subdoc 的"非降级锚点"（check_subdoc.py L228-248）只认 `视角来源:` 字面声明，无法验证该视角是否真跨会话——同会话预演若误标 `跨会话独立Agent` 即可骗过锚点判据。

- 建议：在 SKILL 硬规则 6 附近补一句"来源标记为自证式断言，非运行时验证"的边界说明；并在 `## Human 拍板` 表（原文 L70-77）增加一列"隔离方式（跨provider / 同provider跨会话 / 同会话）"，使收敛时可见真实隔离层级，避免把同会话预演误计入有效覆盖。验收：拍板表能区分三类隔离；SKILL 明确该标记非验证。

**观点 4** — Q3 Phase 2 处置闭环的先决条件"结论须可执行沉淀"不在任何结构闸门内，是最易断的环节
- 发现：子文档 conclusion 模板要求"可执行沉淀指令：改哪些 PRD/ADR、跨子文档约束登记、待删临时脚手架"（原文 L84-89），硬规则 5（SKILL L242-244）明定"conclusion 必须含沉淀指令否则不算闭环"。但 check_subdoc 四不变式（SKILL L196-210）只校验 `状态协议` 与引用越界，完全不校验 conclusion 是否含沉淀指令/指针。sibling-boundary.md L21-24 规定 discuss 阶段 2 只吐 `<conclusion>+<suggested-category>+<pointer>`，最终分类/删除由 zj-docs-ontology 在 Human 确认闭环内完成——但本子文档结论模板没有强制挂"指向 docs-ontology 的指针"字段，briefings/（原文 L63-67 标"阶段 2 删除候选"）也无确定删除清单。

### 视角：O（运维 / SRE / 可靠性·可维护性）
`视角来源: 跨会话独立Agent`

**观点 1** — bug1 的修复必须做成脚本强制，而非给提示词补一句
- 发现：原文 L16-18 明确根因是「该步靠 AI 自觉，无强制」，并承认 launch_pack 启动包已带 intro，但「准备阶段清单未强制」。也就是说失败点正是 AI 自由生成的那段角色推荐清单，目前没有任何脚本形态的产物约束它。
- 影响：若把修复做成「准备阶段提示词加一句请带出简介」，是用新的「靠自觉」修旧的「靠自觉」，根因未消除、复发率≈100%。这是典型的 on-call 式隐性故障：平时不报错，只在 Human 选错角色、后续讨论错位时才暴露，定位成本极高（O.md ② 清单首项即「部署与监控可行性是否验证」）。
- 建议：把「准备阶段角色清单」也纳入发射器产出——扩展 `launch_pack.py`（或新增 prep 生成步骤）从 `role-matrix.md` 直接渲染「key + 一句话简介 + 推荐理由」表格，让 Human 看到脚本产物而非 AI 草稿；并加轻量校验：若 sub-doc 准备阶段清单缺任一已声明角色的 intro，则在后续 `check_subdoc.py` 报违例。验收：用本 sub-02 的声明集跑一遍，确认输出表格每项都带 intro。

**观点 2** — 质量护栏的证据正则过窄，存在误伤摩擦（运维摩擦成本）
- 发现：原文 L19-21 把 check_subdoc.py 四不变式列为质量护栏。读 `check_subdoc.py` L67 可知证据判定正则 `EVIDENCE_RE = "原文\s*[L（("` 只接受「原文 Lxx / 原文（…）」形态；任何「原文 第9-13行」「原文 §2」等非 L 形态引用都会被判「无证据」拒收。
- 影响：误伤率直接转化为运维摩擦——被拒收→Human 改写法→闸门通过率靠格式而非内容。摩擦累积后真实风险是 Human 学会绕过闸门或随便塞一个 `原文 L1` 凑数，护栏可靠性归零。这是 SRE 最警惕的「告警疲劳」式退化（O.md ②「可靠性与线上运维成本是否量化」）。
- 建议：放宽证据正则，接受「原文」+ 任意定位符（行号/区段/章节/小标题），如 `原文\s*(L|第|§|章节|—)` 并容忍中文数字；同时在 `scripts/tests/` 增误伤回归用例（一条用「原文 第9-13行」的观点块必须判通过）。验收：新增用例跑 `python3 scripts/check_subdoc.py` 退出码 0。

**观点 3** — 状态协议只校验「存在」不校验「健康」，缺 on-call 触发
- 发现：原文 L19-21 提到状态协议枚举 DONE/DONE_WITH_CONCERNS/BLOCKED/NEEDS_CONTEXT。读 `check_subdoc.py` L110-134 的 `_check_conclusion`，它只校验「字段存在 + 取值合法 + 未把预演当权威依据」，并不检查子文档是否长期卡在 BLOCKED/NEEDS_CONTEXT。
- 影响：从 O 立场（O.md ②「凌晨被叫醒场景是否覆盖、RTO/RPO 是否明确」），一个子文档长期卡在 BLOCKED、或整文件夹 0 结论就被删除——这种「静默腐烂」没有任何监控/告警。凌晨被叫醒的触发条件（Human 误删未结论集合、长期悬而未决被遗忘）当前护栏完全失明。
- 建议：在 Phase 2 处置契约处加「删除前放行闸门」脚本：遍历 `discussions/<slug>/` 所有 sub-doc，任一 `状态协议` 非 DONE/DONE_WITH_CONCERNS（或缺失 `## conclusion`）即拒绝删除并列出清单；另把「长期 BLOCKED」作为人工巡检项（可在 digest 块标记 oldest-blocked 时间戳），而非靠人记。验收：造含 1 个 BLOCKED 子文档的 fixtures 跑删除闸门，确认被拦截。

**观点 4** — 删除 discussions/ 是破坏性操作，RPO/RTO 与备份职责未定义
- 发现：原文 L22-24 说 Phase 2「Human 确认后删除」。读 `sibling-boundary.md` L21-24 与 `SKILL.md` L39-42，删除前置条件是 zj-docs-ontology 完成「分类沉淀」，但全链路无「沉淀回执」校验，也未说明该文件夹是否在 git 跟踪内、删除前是否 commit。
- 影响：`discussions/` 是「过程权威基座 + 进行中完整解」（`SKILL.md` L35-38）。若 Human 在 ontology 未真正落盘 durable 内容前就删，损失全部 conclusion 与跨子文档约束——RPO 取决于最后一次 commit，若从未提交则 RPO=全丢、RTO=不可恢复。这是最高等级运维风险（不可逆数据丢失），却无任何 alerting/backup 兜底。
- 建议：① 删除前强制 `git add discussions/<slug> && git commit`，把 RPO 锁到删除前、RTO 降到 `git checkout`/reflog 级别；② 要求 zj-docs-ontology 产出「沉淀回执」（哪些 durable 内容已落 docs/、哪些纯过程噪音），删除闸门校验回执存在且非空后才放行；③ 在 `SKILL.md` Phase 4 增硬规则「未持回执 + 未提交 git 的文件夹不得删除」。验收：用 `--dry-run` 删除脚本在「含回执+已提交」fixtures 上验证放行、在「无回执」fixtures 上验证拦截。
