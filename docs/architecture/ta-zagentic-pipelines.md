# ZAgentic pipelines

## Question

What are the two end-to-end flows that bind this repository together — the
installer and validator flow, and the documentation governance flow — and
how does each flow behave from trigger to observable result?

## Scope

This page owns the architecture of two flows: (1) installing and validating
the public and personal skill trees on a supported Agent platform, and (2)
the documentation governance loop that migrates, classifies, and validates
the `docs/` system. Each flow is described as the sequence a Human actually
walks — explicit triggers, allowed sequences, side effects, and observable
evidence. It does not restate each skill's internal workflow (the owning
`SKILL.md` is the source of truth) or the validator scripts' internals.

## Boundaries

- A flow is initiated by **explicit Human intent**, not by a lifecycle
  event. There is no auto-commit, auto-delete, auto-merge hook anywhere in
  the repository; every flow below starts at a prompt or a shell call.
- Any state change that crosses the layer boundaries in
  [ta-zagentic-layers.md](ta-zagentic-layers.md) must produce an observable
  artefact (a generated file, a printed diagnostic, or a commit on the
  current branch).
- Failures in either flow surface as non-zero exit codes, validator
  diagnostics, or a Human-review signal. The flow never silently retries,
  never deletes on failure, and never coerces a conflict into a winner.

## Flow 1 — Install and validate

### Trigger

A Human operator on a supported host runs one of:

- `npx skills@latest add jununfly/ZAgentic` (network install), or
- `scripts/link-skills.sh [--platform <name>] [--method copy|symlink] [--dry-run]`
  (local clone install), or
- `scripts/validate-plugin.sh` (validate without installing).

### Sequence

| Step | Actor | What happens | Side effect |
| --- | --- | --- | --- |
| 1 | Human | Picks a platform and a method on a local clone. | None yet. |
| 2 | Installer (`link-skills.sh`) | Iterates `skills/<bucket>/zj-*` and `personal/zj-*`; for each, resolves the target directory (`~/.claude/skills`, `~/.codex/skills`, `~/.workbuddy/skills`) and either copies or symlinks the skill. With `--dry-run`, prints the plan only. | Skill folders appear under the chosen target. |
| 3 | Agent platform | On its next startup or plugin scan, the platform enumerates the skill folders. | The skills become invokable. |
| 4 | Human | Runs `scripts/validate-plugin.sh` whenever the layout or a skill is changed. | None yet. |
| 5 | Validator orchestrator | Runs the official plugin validator if available; otherwise runs `scripts/validate-zagentic-plugin.py`. | Prints pass/fail and exits. |
| 6 | Recursive plugin validator | Walks `skills/` recursively, checks bucket registration, runs `validate-skill-frontmatter.py` on every `SKILL.md`, checks bucket `README.md` coverage, and confirms top-level README registrations. | Emits diagnostics with stable codes; non-zero exit on mechanical failure. |
| 7 | Git safety wrapper | For every Git operation, the Human uses `./scripts/zj-git` (or `env -u NODE_OPTIONS git`) to bypass the WorkBuddy safe-delete shim on Windows Git Bash. | The `rm -rf` path is never reached by Node `fs.*` calls; `.git/` state survives. |

### State and effects

- The repository working tree, the installed skill folders, and the
  platform's skill index are the three observable surfaces.
- Installed state mirrors local state at install time and does not auto-sync.
- No state is copied into `docs/`, `research/`, or `skills-outputs/` by the
  flow.

### Failure or exit behavior

- A non-zero exit from the frontmatter validator, the bucket-README check,
  or the registry check stops the flow at step 6. The Human reads the
  diagnostic, fixes the upstream cause, and re-runs the validator.
- A `--dry-run` for the installer prints the plan, exits zero, and writes
  nothing.
- A Git operation that the shim corrupts is recovered through
  `zj-git-bypass-safe-delete`; the safe-delete shim is the failure source,
  not the Git binary.
- The platform's own skill enumeration is out of this flow's control; if
  the platform fails to enumerate after install, that is a platform
  problem to report upstream.

### Observable evidence

- `scripts/zagentic-skills-list` (regenerated by `scripts/list-skills.sh`)
  enumerates the final catalogue.
- The validator's diagnostics on stdout, with stable codes
  (`PAGE_*`, `SOURCE_*`, `MAP_*`, `AUTHORITY_*`).
- A new `SKILL.md` appears under the chosen target directory.

## Flow 2 — Documentation governance

### Trigger

A Human prompts `zj-docs-ontology` for one explicit governance task. Common
triggers are: greenfield establishment, post-migration validation, or
drift detection after a round of changes. Auto-triggers are explicitly
forbidden by the Codebase Docs capability spec.

### Sequence

| Stage | Skill / owner | What happens | Side effect | Failure mode |
| --- | --- | --- | --- | --- |
| 1. Discover | `zj-docs-ontology` | Reads the explicit `docs-map:` pointer in `AGENTS.md`, `CLAUDE.md`, or `README.md`; falls back to `docs/README.md`; otherwise proposes a single compatible candidate or surfaces ambiguity. | None. | Ambiguity is reported; nothing is written. |
| 2. Classify | `zj-docs-ontology` | Inventories each Markdown file under `docs/`, plus the root context entries; classifies as long-lived authority, external reference, fixture documentation, process material, or evidence surface. | None (read-only). | Contradictory classifications surface as a Human-review signal. |
| 3. Propose | `zj-docs-ontology` | Produces the smallest map and the minimum lazy categories required; for an existing system, produces a migration plan naming every move, link repair, rewrite, and deletion. | None (read-only proposal). | Unresolved authority conflict halts the proposal. |
| 4. Confirm | Human | Reviews the proposal; explicitly confirms each move, rewrite, and deletion. | None (consent only). | A withheld consent returns the flow to step 3. |
| 5. Execute | `zj-docs-ontology` orchestrating `zj-domain-modeling`, `zj-docs-architecture`, `zj-debrief`, and `zj-neat-freak` as applicable | Applies the `git mv` operations, repairs links, performs the approved rewrites, schedules the approved deletions. | The repository working tree changes; commits are made per approved slice. | A scoped slice failure stops the rest of the execution. |
| 6. Validate | `validate_architecture_docs.py` from `zj-docs-architecture`, plus the documentation-system validator if invoked | Walks the new map, every long-lived page, the ADR metadata the pages cite, and the source-map targets; emits mechanical codes and Human-review signals. | Prints diagnostics; non-zero exit on mechanical failure. | A mechanical failure surfaces the responsible page and its failing diagnostic; the Human decides whether to revise the page or to step back to stage 5. |

### State and effects

- The mutated artefacts are the map (`docs/README.md`), the long-lived pages
  in their declared categories, and the ADR metadata when an ADR is
  accepted or superseded.
- Process material (`docs/zj-retros/`) accumulates only through `zj-debrief`
  during this flow and is not deleted in the same execution.
- Evidence surfaces (`research/`, `skills-outputs/`) are not moved or
  governed by this flow.

### Failure or exit behavior

- Mechanical validator failures (`MAP_*`, `PAGE_*`, `AUTHORITY_*`,
  `SOURCE_*`, `ADR_*`) halt the flow at step 6 with a non-zero exit. The
  Human decides whether to revise the proposal or to revise the underlying
  page.
- Human-review signals (`SIGNAL_*`) report but do not fail the flow; the
  Human acknowledges them.
- A scope failure inside stage 5 stops the rest of the execution; the
  slice is reverted by `git revert` on its scoped commit.
- Process-material deletion is a separately confirmed action; it never
  rides on the same confirmation as a move or rewrite.

### Observable evidence

- A diff per slice after stage 5; the proposed diffs are the same diffs
  the validator inspects.
- The validator's final report at stage 6.
- The `docs/` tree's new shape and `docs/README.md` updated routing.
