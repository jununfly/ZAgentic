# 过程角色（Process Roles）— 编排层范式的整包 adapt

> 来源：`design.md §10.2 / §10.4 项2`。借鉴开源「角色 = 带闸门的过程」范式，取 **domain 无关流程角色**
> （`/office-hours` 问题重构、`/plan-*` 评审闸门、`/retro` 收尾复盘）作为编排层步骤。
> **只取结构、剥离软件专用措辞**（如 ship / PR / CI），不进视角角色集，不占独立视角覆盖，
> 不引入运行时 / 共享状态（见 `design.md §8` 集成边界与 §10.6 R2）。

这些角色由**主力Ai（主会话编排者）**持有，属于「怎么把讨论组织好」的元步骤，
与「13 个独立视角角色（B/C/A/…）」正交。视角角色回答「问题是什么」，
过程角色保证「讨论过程本身质量过关」。

---

## ① `office-hours` → 准备阶段·问题重构

**范式原义（软件交付语境）**：用一连串提问把模糊需求重构为可解问题。

**本方法适配（Phase 1 准备阶段，由 lead AI 执行）：**
- 把核心问题拆成**可独立验证**的子问题，每个子文档对应一个。
- 重构后的子问题须满足三条，否则回到解构、不进入讨论：
  1. **一事一议**：边界清楚，不与其他子问题重叠。
  2. **独立可解**：不依赖另一个子问题先出结论才能开工。
  3. **成功判据可验证**：能写出「怎样算解决」的判据（呼应固定议程 F1）。
- 产出 = 每个子文档的 `## 待讨论问题（scope 草案）` 的 Q1/Q2/…。

**闸门**：重构不达标 → 禁止进入 Phase 2；不做「大而化之的一团问题」。

---

## ② `plan-*` → 评审闸门（scope / 架构 / UX）

**范式原义（软件交付语境）**：scope / 架构 / UX 评审作为把关点，不过审不推进。

**本方法适配（嵌入 Phase 2 动态议程决策函数 与 Phase 3 合成前）：**
在「触发 F5 合成 / 标 conclusion」之前，编排层强制过三道闸门，不过则不准收敛：

- **scope 闸门**：本子文档是否真独立、是否越界（越界内容是否应回填 MASTER 跨子文档约束）。
- **架构闸门**：方案是否守住边界 / 不变式（与 A 视角呼应，但此处是编排层自检，非替代 A 视角）。
- **UX 闸门**：是否从真实使用现场出发（与 U 视角呼应，同上）。

**只取结构**：闸门是「收敛前的必过检查点」，不是把软件交付评审项搬进来。
具体评审结论仍由各独立视角角色（A/U/…）在其 gated method 中产出。

---

## ③ `retro` → 收尾复盘

**范式原义（软件交付语境）**：retro 沉淀 learnings，闭环改进。

**本方法适配（Phase 3 终局合成后 / Phase 4 处置前，由 lead AI 执行）：**
对照 `MASTER.md` 解决思路与 **R4 度量注册表**（`scripts/metrics.py` 的
`compression_ratio`、闭合率等），跑一次收尾复盘，回答：

1. 本次讨论是否**完整**？哪些开放问题被遗漏或草草收场？
2. 各声明角色的**有效覆盖**是否真实（有无回声 / 低质被标 `同会话SubAgent`）？
3. 下次怎么改进（问题重构更准 / 角色集更对 / 闸门更严）？

**learnings 落点（呼应 §8 集成边界）**：复盘结论沉淀进设计文档三件套
（`product.md` / `architecture.md` / `design.md`），**不**引入共享 learnings 运行时 /
共享状态。即「薄层复用」，符合 C 分类与 B1 仅限范式的红线。

---

## 红线（不可越过）

- 过程角色**不引入运行时 / 共享状态**——它们是主会话里的编排步骤，不是独立 Agent。
- **只取结构、剥离软件专用措辞**：不出现「ship / PR / CI / 部署流水线」等软件交付语境；
  出现的只能是「问题重构 / 评审闸门 / 收尾复盘」这类方法结构。
- 过程角色**不挤占**独立视角覆盖：收敛判定仍只看声明必需集（视角角色）是否全覆盖。
