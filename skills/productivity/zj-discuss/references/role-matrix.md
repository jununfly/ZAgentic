# Role Matrix（可复用角色矩阵 + 候选池）

用于 `zj-discuss` 每子文档的独立多视角讨论。角色是**结构差异**，不是同一
镜头的换名——每条都带不同的「差异锚点」，确保视角真的错位而非回声。

本文件是角色语义的**唯一真源（SSOT）**：`zj-discuss` / `zj-discuss-view` 只引用、
不复述，避免概念漂移。

## 两类角色

**编排者（主会话，非独立视角）：主力AI**
- 立场：产品实用主义 + 架构整合，是运行 `zj-discuss` 的**主会话编排大脑**。
- 负责：分解、准备阶段角色推荐、动态议程编排、合成回卷、写「主力AI 整合立场」区块。
- **不是**跨会话独立视角，明确标 `视角来源: 同会话SubAgent(低权重)`，
  **不计入**下面的独立视角覆盖。
- 措辞约定：这里的「低权重」指**非隔离、整合型**，绝不等于「弱」——主力AI 是
  编排核心，份量高；它只是不提供跨会话隔离，故其产出**永不可作为结论权威依据**。

**独立结构视角（须跨会话独立 Agent）：从候选池按子问题选取**
| key | 角色 | 默认 | 结构立场 | 差异锚点（它天然追问什么） | 一句话简介 |
| --- | --- | --- | --- | --- | --- |
| B | 技术经理 | ✅ | 可落地 / 工程现实 | 排期、依赖、风险、谁来做、做到什么程度算完 | 把方案从"能说"逼到"能做"，专问落地与代价 |
| C | 产品专家 | ✅ | 用户价值 / 生态·竞品参照 | 用户是谁、愿不愿意用、优先级、生态/竞品参照 | 站在使用者与生态位置，问"凭什么用、值不值" |
| A | 架构师 | ✅ | 约束 / 长期一致 | 边界、不变式、向后兼容、与其他系统的耦合 | 守护长期一致性与边界，专问"以后会不会炸" |
| T | 测试 / 质量 | ⚪ | 可验证性 / 验收 | 怎么测、验收标准、边界 case、回归风险 | 把"觉得对"变成"能证明对"，专问验证与质量 |
| S | 安全 / 威胁建模 | ⚪ | 攻击面 / 威胁 | 权限、数据泄露、攻击面、合规边界 | 站在攻击者视角，专问"哪里会被打穿" |
| O | 运维 / SRE | ⚪ | 可靠性 / 可维护性 | 部署、监控、可靠性、线上运维成本 | 站在凌晨被叫醒的人视角，专问"上线后怎么死" |
| D | 数据 / 数据建模 | ⚪ | 数据一致性 / 建模 | 数据模型、存储、ETL、一致性、量级 | 站在数据生命周期视角，专问"数据怎么存怎么错" |
| L | 法律 / 合规 | ⚪ | 协议 / 监管 / 许可 | 开源许可、隐私、监管、协议风险 | 站在合规与风险视角，专问"会不会违法/违约" |
| F | 财务 / 成本 | ⚪ | 预算 / ROI / 资源 | 投入、回报、计费、资源占用 | 站在花钱的人视角，专问"值不值这个价" |
| U | 用户研究 / UX | ⚪ | 交互 / 可用性 / 体验 | 用户流程、可用性、体验摩擦 | 站在真实使用现场，专问"人用起来顺不顺" |
| R | 学术 / 研究严谨 | ⚪ | 理论正确性 / 方法学 | 文献、方法学、理论边界、可复现 | 站在严谨方法视角，专问"论证站不站得住" |
| P | 流程 / 组织协作 | ⚪ | 落地推手 / 协作 | 团队、流程、跨角色协作、推进阻力 | 站在"让事发生"的推手视角，专问"谁来做、怎么推" |
| E | 伦理 / 社会影响 | ⚪ | 公平 / 偏见 / 社会影响 | 偏见、公平、社会影响、AI 安全伦理 | 站在社会与受影响者视角，专问"长期代价与公平" |

> ✅=默认必需集成员（base）；⚪=候选池，按问题意涵按需选取。
> C 的「市场」原义对 **solo 使用者（无真实市场/竞品压力）几乎空转**——故改写为
> 「用户价值 / 生态·竞品参照」，贴合 zj 的语境，避免产生空洞视角。
> 因此 **C 的闸门阈值在 solo/内部子问题降为 N=2**（有真实市场信号回 N=3），避免视角注水萎缩；
> 详见 `role-methods/C.md` ⑤ 与 `design.md` §10.6.1 R1（跨会话复核 2026-09-29 已锁定）。

> **每个角色均有 gated method（带闸门的 executable 方法）**：`references/role-methods/<key>.md`
> （`<key>` ∈ {B,C,A,T,S,O,D,L,F,U,R,P,E}）。角色语义（立场 / 差异锚点）以本文件为唯一真源；
> 方法文件是「牙齿」——把一句话立场变成可机械判定的核查契约（① Read 原文 ② 角色专属核查清单
> ③ 强制输出结构 ④ 闸门）。角色 Agent 动笔前应 `Read` 对应方法文件。过程角色（非视角角色）见
> `references/process-roles.md`。

## 推荐启发式（准备阶段用）

`zj-discuss` 在**准备阶段**依据复杂问题 / 子问题的**意涵信号**推荐角色集，
再交 Human 调整。规则：

1. **base 集 {B, C, A} 永远推荐**（覆盖 执行 / 产品·市场 / 架构，最普适）。
2. **问题信号 → 追加可选角色**（满足任一信号即建议加入）：

| 信号（子问题触及…） | 建议追加角色 |
| --- | --- |
| 验收标准 / 代码 / 接口契约 / 可测行为 | T（测试·质量） |
| 权限 / 数据泄露 / 攻击面 / 合规边界 | S（安全） |
| 部署 / 监控 / 可靠性 / 线上运维 | O（运维·SRE） |
| 数据模型 / 存储 / ETL / 一致性 | D（数据） |
| 协议 / 隐私 / 监管 / 开源许可 | L（法律·合规） |
| 预算 / ROI / 资源投入 / 计费 | F（财务·成本） |
| 交互 / 可用性 / 用户流程 / 体验 | U（用户研究·UX） |
| 理论正确性 / 文献 / 方法学 | R（学术·研究） |
| 团队 / 流程 / 跨角色协作 / 落地推手 | P（流程·组织） |
| 偏见 / 公平 / 社会影响 / AI 伦理 | E（伦理·社会） |

3. **准备阶段呈现方式**（见 `zj-discuss` SKILL.md 的准备阶段）：
   - 先给「**推荐参与角色**」清单：每个角色带**一句话简介** + 推荐理由
     （命中了哪条信号 / 为什么 base）。
   - 再给「**其他可选角色**」清单：候选池中未被推荐的，每个也带**一句话简介**，
     支持 Human 按自己的判断增删。
   - Human 确认/调整后，锁定的集合成为该子文档（或整场讨论）的
     **declared required set（声明必需集）**，用于收敛判定。

## 默认集与收敛规则（硬，参数化）

- **收敛停规则参数化**：当「本次声明的必需集」全部覆盖即停。base {B,C,A}
  只是该参数的常用取值；加 T/S/… 后即以扩展集为停条件。主力AI 是整合者，不计入覆盖。
- **按需增删不死板**：仅当子文档触及对应信号才挂该可选角色；纯讨论/设计类
  不挂。增删走既有「声明必需集 → 覆盖即停」出口，不破坏不变式。
- 高利害、易回声室的子问题 → 用**跨会话独立 Agent**（真隔离，权重高）。
- 分解 / 合成 / 核验等结构性辅助 → 可用**同会话 SubAgent**（低隔离，低权重）。

## 已验证的坑（来自真实跑通）

- **同会话角色扮演 ≠ 运行期隔离。** 同一 context window 内扮演多角色权重应低于
  跨会话独立视角——它无法摆脱首轮锚定，易退化成回声室。
- **回声室真实存在。** 不强制结构化错位，多视角只会互相加固首轮结论。
- **结论必须给可执行沉淀指令**（改哪些 PRD/ADR、删哪个临时文档），否则
  讨论悬空、不算闭环。

## 用法

`zj-discuss` 为每子文档的**声明必需集中的每个角色**各生成一份 briefing，每份盖章
角色立场 + 强制 `Read` 原文令；Human 复制到跨会话独立 Agent 加载
`zj-discuss-view --role X <sub-doc路径>` 撰写（X ∈ 声明必需集，可为候选池中任一 key
或 Human 自定义 key）。**主力Ai 整合立场在主会话直接写，不走 briefing。** 角色语义
一律以本文件为**唯一真源**；每个独立视角角色还须按 `references/role-methods/<key>.md`
的 gated method 产出（核查清单 + 三字段观点 + 闸门），否则不计入有效覆盖。
